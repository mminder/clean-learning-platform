# Decision log

The design decisions agreed on 2026-11-07, when the [initial spec](archive/initial-spec.md) was refined, and the ones made since, each with its date. Each entry gives the decision and the reason for it. When a decision changes, edit its entry and note the date.

## Access and roles

- **D-01 Public shop.** Visitors can browse the shop and offering details without logging in; buying requires login. Customers are always individuals buying for themselves (no B2B seats). *Why:* this is how a public internet shop works, and it costs nothing extra.
- **D-02 Multiple roles per user.** A user can hold any combination of `CUSTOMER`, `EXPERT` and `ADMIN`; Admin + Expert is the typical case. *Why:* small organisation, one person often has several jobs.
- **D-03 Union navigation.** The header shows a section for every role the user holds; there's no role switcher. The landing page follows the priority Expert → Admin → Customer. Every role combination is allowed. *Why:* no mode switching, and nothing special in the backend.
- **D-04 Roles live in our DB.** In the MVP, a first OIDC login creates the user with `CUSTOMER` (just-in-time provisioning), and an admin grants or revokes `EXPERT`/`ADMIN` ([UC-19](use-cases/uc-19-manage-users.md)). The PoC has seeded users only. *Why:* the IdP only answers "who is this"; authorization stays inside the app and testable there.

## Catalog

- **D-05 Packages and prices.** A consultation offering has packages (session count + price). A training has one price for all its runs. "Buy" on a card opens the same picker-plus-confirmation dialog as on the detail page. Prices are CHF including VAT, modelled as a `Money` value object. *Why:* matches "session counts" in the spec, and treats packages and runs alike.
- **D-06 Eligible experts.** The admin assigns eligible experts to each consultation offering, and the customer picks from them on the first booking. An expert who is also a customer may pick themself. *Why:* a career coach shouldn't appear in an architecture consultation. Self-selection is handy for testing, and it replaces an earlier "not your own case" guard.
- **D-07 Offering lifecycle.** `DRAFT → PUBLISHED → ARCHIVED`. Only published offerings appear in the shop. Publishing checks completeness. Unpublish (back to draft) and hard delete are allowed only without purchases; otherwise the admin archives. A run can be deleted only without enrollments. *Why:* no half-built offerings in the shop, and purchased data is never destroyed.
- **D-08 Purchase terms and run schedules.** At purchase, the terms are copied into the case or enrollment (price paid; for consultations also session count, session duration and cancellation deadline). Creating a run copies the day template into a concrete dated schedule. A run's dates are locked once anyone is enrolled. Name, description and image are always read live. *Why:* customers get what they bought, and later edits never rewrite history.

## Consultation

- **D-09 Availability.** An expert selects calendar dates plus one set of daily time ranges that applies to all of them. Free time = availability − booked appointments − time slots of assigned runs. Removing availability never cancels appointments. Assigning an expert to a run is blocked if it overlaps the expert's busy time. Dates before today (Zurich) can't be changed, and time ranges may neither overlap nor touch (added 2026-11-09, with UC-13). *Why:* matches "calendar" in the spec, handles vacations without exception logic, and prevents double-booking.
- **D-10 Slot generation.** Start times on a 30-minute grid, no buffer between sessions, at least 24 h notice, and any number of bookings up to the open credits. These are constants in one domain class. The grid and the availability ranges are Zurich wall-clock times, and a session lasts its real duration: a start time is offered only if it exists exactly once on its date, and the session ends, as an instant, at or before the end of its range (added 2026-11-09, with UC-06; this only matters on the days of the summer-time changes). A customer's appointments never overlap: a start time whose session overlaps one of the customer's own booked appointments, of any case, isn't offered and can't be booked. The booking doesn't lock the customer, so two bookings by one customer at the same instant, on two cases with two experts, could still overlap; that's accepted (added 2026-11-09 by the product owner, [spec 04](specs/04-book-consultation-appointment.md#decisions), decision 22). *Why:* simple, and easy to test and change.
- **D-11 Cancellation deadline and consumption.** The cancellation deadline is a duration in hours configured per offering (examples: 24 h for career coaching, 168 h for trainings). Cancellation is free before `start − deadline`. An appointment is consumed once its start has passed, and attendance isn't tracked. Open credits = total − booked − forfeited, always computed. The current time comes from an injected `Clock`. *Why:* clear definitions for the refund rules, and no counter that can drift.
- **D-12 Case lifecycle.** `ACTIVE` and `CANCELLED` are stored, and `COMPLETED` is derived. Credits never expire. Cancelling an active case is always allowed, with a warning when it's not refund-eligible. Refund-eligible means no consumed appointment, no forfeited credit, and every future booked appointment still before its deadline. The future appointments cancelled with a case follow the appointment's rule at that moment: refunded before their deadline, forfeited after (added 2026-11-13, with UC-08). A cancellation request names the outcome the customer confirmed, and a changed one is a 409 (added 2026-11-13, with UC-07 and UC-08, as for the price and the expert). The customer doesn't see cancelled appointments; the open credits show the outcome (decided 2026-11-13 by the product owner). *Why:* the same "cancel with warning" model as for appointments.
- **D-13 Goodwill credit adjustments.** An admin adds adjustment entries: a ± delta, a mandatory reason, the admin, and a timestamp. Open credits can't drop below 0. Cancelled cases can't be adjusted. *Why:* an audit trail for support cases at almost no cost.
- **D-14 Notes.** Notes belong to the case and are plain text. The assigned expert can create, edit and delete them and switch between private and public. The customer sees public notes; the admin sees no notes. A case appears in an expert's list only after the first booking. *Why:* the spec's privacy rule, made explicit for every role.

## Training

- **D-15 Buying a run.** A run can be bought until its first time slot starts while seats are free, and a customer can enroll in a run only once. The shop shows "N seats left" or "Sold out". Seats are set per run, with the default taken from the training, and can't be set below the enrolled count. Selling doesn't require an assigned expert ("to be announced"). A cancellation frees the seat. *Why:* simple and predictable; no waitlist.
- **D-16 Cancelling an enrollment.** Allowed until the run starts. It's refund-eligible only before the deadline, which is measured from the first time slot. `ENROLLED` and `CANCELLED` are stored, and `COMPLETED` is derived. Cancelling a whole run is out of scope. *Why:* mirrors the consultation rules; a started run can't be resold anyway.

## Views and calls

- **D-17 List ordering.** "My …" lists are grouped into Upcoming (by next date), then Needs booking (active case with open credits and nothing booked), then Past (completed or cancelled, collapsed, newest first: a completed case by its last appointment, a cancelled one by its cancellation time; added 2026-11-13, with UC-08). Expert trainings are sorted by next run date. An appointment is upcoming until it ends, though consumed from its start, so its case stays under Upcoming while the session runs (added 2026-11-09, with UC-10). *Why:* unbooked cases don't get lost, and a running session is found where the next one is.
- **D-18 What experts see.** An expert sees only their own runs, with participants (name and email). On cases, the assigned expert sees the customer's name and email. *Why:* experts need to reach participants, and there's no in-app messaging.
- **D-19 Teams links.** Each run has one Teams link set by the admin. Consultations use the expert's personal Teams link from their profile ([UC-14](use-cases/uc-14-manage-expert-profile.md)). Customers see a link from 1 h before start until the end; experts always see it. *Why:* no MS Graph integration needed.

## Cross-cutting

- **D-20 Defaults.** Time zone `Europe/Zurich` (instants stored as `timestamptz`, local times for slots and availability); English UI only, without i18n; no email notifications; GDPR features are future work; every table has `created_at` and `updated_at`. *Why:* YAGNI for a PoC/MVP.
- **D-21 Images.** Upload per entity (offering image, expert photo), stored in a Postgres `image` table behind an `ImageStorePort` and served at `GET /api/images/{id}` with long cache headers (a replaced image gets a new id). JPEG, PNG or WebP, at most 2 MB, no resizing. The type is detected from the file's first bytes, not from its name or the declared content type (2026-11-08, with the first upload in UC-16; the port was called `ImageStore` before, but every port's name ends in `Port`). *Why:* image management is in scope from the PoC, and storing images in the database needs no extra infrastructure.

## Architecture

- **D-22 Layer-first packages.** Root packages `api`, `application`, `domain`, `adapters.database`, with feature sub-packages inside each. ArchUnit enforces the layer rules. No Spring Modulith. *Why:* the layout the spec asked for.
- **D-23 One shared schema with narrow ports.** The features are `user`, `offering`, `consultation`, `training`, `availability`, `image` and `shared`. Each use case defines narrow ports, and database adapters may join across feature tables. Feature isolation isn't enforced. *Why:* coupling lives in SQL behind narrow ports instead of in shared domain classes, and no split into services is planned.
- **D-24 No Order entity yet.** Buying a package creates a case and buying a run creates an enrollment, each with its own price and refund data. An `order` feature arrives together with real payment. *Why:* until payment exists, an Order would only be a pass-through table.
- **D-25 Authentication.** Backend-for-frontend (BFF): Spring Boot is the confidential OIDC client, and the SPA only holds an HttpOnly session cookie. In the PoC, `POST /api/poc/login` creates the same session and exists only in the `poc` profile. `GET /api/me` behaves identically in both modes. Keycloak runs locally; the production IdP is open. *Why:* the current recommendation for browser apps, and swapping in real login doesn't touch the SPA.
- **D-26 Authorization** (changed 2026-11-10; before, only `SecurityConfig` checked the roles, per route prefix). Each controller says who may call its routes with `@PreAuthorize`, at class level: `hasRole(...)` for the controllers under `/api/customer`, `/api/expert` and `/api/admin`, `isAuthenticated()` for `/api/me`, and `permitAll()` for the shop, the images and the PoC login. The prefixes stay and name the role, and `SecurityConfig` still checks it per prefix, as a coarse first line; everything else passes on to the annotations. Deny by default, at build time: ArchUnit fails for a route without `@PreAuthorize`, and for anything that would skip the check silently. Ownership is enforced in the use cases through scoped queries, returning 404 when a resource isn't yours. Tests are REST integration tests: a role matrix, which fails for a route without a row, plus ownership checks using the two seeded users per role. *Why:* the rule sits on the code it guards, and a forgotten one fails the build instead of letting every logged-in user in. But the annotation is checked only after Spring MVC has read and validated the request, so the prefix check turns a caller without the role away first, before any body, such as an image upload, is parsed. The real filtering lives in SQL, so only tests against a real database prove it.
- **D-27 Concurrency.** The use-case transaction takes pessimistic row locks on the contended parent row, always in the order offering → case → expert → run. Every change to an offering locks its row first, so two status changes can't both pass and an archived offering stays read-only (offering added 2026-11-08, with UC-16). So does a purchase of a consultation package, which needs the offering published; unpublish and delete check for purchases under the same lock, so a purchase and an unpublish can't both pass (added 2026-11-09, with UC-03). A booking locks the case, then the expert's user row, and re-checks every rule under the locks. Saving availability locks the expert's user row too, so two saves can't interleave, and a booking sees either the old or the new availability (added 2026-11-09, with UC-06 and UC-13). Cancelling an appointment or a case locks the case, and a booking checks under its case lock that the case isn't cancelled, so a case cancelled while a booking runs never keeps a future booked appointment (added 2026-11-13, with UC-07 and UC-08). *Why:* this covers every rule, including overlaps across tables, without retry logic.
- **D-28 Backend tooling.** Java 25, Spring Boot 4.x, Maven, Spring Data JPA/Hibernate, hand-written mappers, records without Lombok, Flyway (schema plus seed for `poc`/`dev`), Bean Validation on request DTOs, `ProblemDetail` errors, JUnit Jupiter 6, AssertJ, Testcontainers, ArchUnit, `MockMvcTester`, and an injected `Clock`.
- **D-29 Frontend tooling and API contract.** Vite, React, TypeScript (strict), npm, React Router, TanStack Query, shadcn/ui, Tailwind, React Hook Form, and date-fns with `@date-fns/tz`. The API is code-first: springdoc generates `backend/openapi.json`, which is committed, and openapi-typescript plus openapi-fetch generate the frontend client. A test fails if the committed spec is stale. The OpenAPI document at `/v3/api-docs` stays public in every profile, including production (decided 2026-11-08): it describes the routes, not the data, and every route keeps its own access rule. Frontend tests use Vitest only where there's logic; Playwright arrives in the MVP.
- **D-30 Repository and runtime.** A monorepo with `backend/`, `frontend/`, `_docs/` and `docker-compose.yml` (Postgres, Keycloak). Production is one container: the Spring Boot jar serves the built SPA. Hosting is decided at MVP time. CI runs on GitHub Actions from the first increment (changed 2026-11-07; it was deferred to the MVP before). *Why:* agents deliver their work as pull requests and need automatic feedback from the start.
- **D-34 Error responses** (decided 2026-11-08). Errors raised inside Spring MVC are `ProblemDetail` bodies (400, 404, 405, later 409). Spring Security's 401 (empty body) and 403 (Boot's error JSON), and unexpected 500s (Boot's error JSON), stay status-only: clients rely on their status, never on their body. The task that first needs an error body in the frontend adds one shared `ProblemDetail` schema to `openapi.json`: `type`, `title`, `status`, `detail` and `instance`, plus `code` for 409 and the field list for 400 (added with UC-16's form, [increment 02](tasks/02-manage-consultation-offerings/03-create-and-edit-consultation-offering.md); `type` is optional, because Spring leaves it out when it's `about:blank`). That's the 400 field list of [UC-16](use-cases/uc-16-manage-consultation-offering.md)'s form, and UC-16's first 409 adds `code` (changed 2026-11-08 while planning [spec 02](specs/02-manage-consultation-offerings.md); the first 409 was expected to come first). The frontend type stays generated, with no hand-written error DTO. A 409's `detail` is written for the user, and the frontend shows it; `code` is stable, for code that reacts to one conflict and for tests (decided 2026-11-08). *Why:* the SPA reacts to 401, 403 and 500 by their status alone (login, not allowed, try again), so uniform bodies there would be code nobody reads. One generated schema keeps the frontend's API types generated once it does read a body, and waiting for the first body the frontend reads avoids building it before it's needed.
- **D-35 Use-case naming** (decided 2026-11-08). A use case is one `@Service` class named `<Verb><Noun>UseCase`, e.g. `GetShopOfferingUseCase`. Its one public method is named `invoke`. `LayerRulesTest` checks both. Until then the suffix was `Service` and the method was named after the action (`get`, `list`). *Why:* the name says what the class is in this architecture, a use case, rather than which Spring stereotype it carries. The class name already holds the verb, so the method doesn't repeat it.
- **D-36 Value objects** (decided 2026-11-08). A domain value is a value object when it has a rule beyond not null (`OfferingName` and `DisplayName` are never blank, `SessionCount` is at least 1), a unit (`SessionDuration` in minutes, `CancellationDeadline` in hours) or behavior (`Money` compares), or when it could be mixed up with another value of the same type (typed ids). Other values stay Java types: an offering's description and an expert's bio are `String`s and may be empty. A column that holds a value object repeats its rule as a check constraint. *Why:* the rule lives in one place and holds in every model that carries the value, and text without a rule doesn't get a wrapper that only adds `.value()` calls. The check constraint keeps invalid rows out of the database, so the domain never throws on data it reads, which would turn a whole list into a 500.
- **D-37 Role sub-packages** (decided 2026-11-08; `port` added 2026-11-09, `read` 2026-11-14). In a feature package, the classes that do the work sit at the top: controllers in `api.<feature>`, use cases in `application.<feature>`, adapters and Spring Data repositories in `adapters.database.<feature>`, models in `domain.<feature>`. A use case's command records sit next to it, because they are part of its signature. The types they use sit in a sub-package per role: `response` and `request` in `api.<feature>`, `port` (outgoing ports) in `application.<feature>`, `entity` (JPA entities) and `row` (records a query selects into) in `adapters.database.<feature>`, and `value` (value objects) and `read` (read models, objects shaped for one page or answer, such as `ShopOffering` or `CustomerConsultationCase`) in `domain.<feature>`. A read model may use the models, never the other way round, and throws no `BusinessRuleException`; a part of a model, such as `ConsultationPackage`, stays next to its model. Types that several features share follow the same rule, in `api.response` and `domain.shared.value`. The entities, the rows and the responses' `from(...)` methods are public, because the parent package uses them; the layer rules still keep them inside their layer. ArchUnit checks where entities, rows, responses and ports live, that a value object depends only on Java and other value objects, and both rules of the read models. The ports are a layer of their own in `LayerRulesTest`: only use cases and adapters use them, and they use only domain types. *Why:* a feature package collects many small supporting types as it grows, an entity per table, a row and a response per query, and the ports its use cases need, and a domain package mixes models that hold rules with read models that only show them. In sub-packages they don't bury the classes that do the work, and the package says what a type is, so ArchUnit can check that it sits where it belongs. For the ports it checks both sides of the hexagon as well: controllers reach only the use cases, adapters only the ports.
- **D-38 Java formatting** (decided 2026-11-13). Java code is formatted by google-java-format in its default style (2-space indent, 100 columns), run by the Spotless Maven plugin. `./mvnw verify` fails on unformatted code; `./mvnw spotless:apply` formats it. A declaration that doesn't fit on one line gets one record component or parameter per line. *Why:* one formatter without options ends style discussions in reviews and agent output, and long record headers become readable.

## Scope and docs

- **D-31 PoC vs MVP.** The PoC covers UC-01 to UC-18 with the fake login and no money. The MVP adds OIDC login, user management (UC-19), payment and refunds, Playwright E2E, and hosting. (CI moved into the PoC on 2026-11-07, see D-30.) Two pairs of spec use cases were merged: the customer and expert "takes part in call" became [UC-10](use-cases/uc-10-join-call.md), and "Admin views all trainings" became part of [UC-17](use-cases/uc-17-manage-training-offering.md).
- **D-32 Docs and agent instructions.** The `_docs/` structure is shown in [README.md](README.md), with one file per use case and this single decision log. There is only an `AGENTS.md` and no `CLAUDE.md`, because Claude Code ≥ 2.1.277 reads `AGENTS.md` when no `CLAUDE.md` exists.
- **D-33 Increments, specs and tasks.** Work is planned in increments. Each increment has a spec in [specs/](specs/README.md) (what and why, with WHEN/THEN scenarios) and a folder in [tasks/](tasks/README.md) (a technical plan, plus one file per task that fits one agent session, marked AFK or HITL). The use cases keep describing the finished system; a spec only says which part is built now. The first increment is a tracer bullet through every layer, using the consultation part of UC-02. The format borrows from OpenSpec and from Matt Pocock's planning skills. An orchestrating session executes an increment ([tasks/README.md](tasks/README.md#executing-an-increment)): per task, one implementing subagent (in its own git worktree where tasks run in parallel), then a review subagent that fixes the major findings, then a merge of the task into the increment's branch. After the last task, an overall review of the whole change and a fixer for its major findings. The whole increment is one pull request (changed 2026-11-08; before, each task was one agent session and one pull request). *Why:* agents need small, checkable units of work, and a thin end-to-end path retires the integration risks before any business rule is built. A fresh subagent per task keeps each context small, the reviews catch what the implementer missed, and the product owner reviews one pull request per increment instead of one per task.
